# FeishuBrief 产品化与邮箱自主注册后续方案 V1

日期：2026-09-26

状态：后续产品方案，尚未启用公开注册。

适用基线：Phase 4 组内邀请制成员服务。

## 1. 决策与阶段边界

当前服务组内使用：管理员邀请指定邮箱，成员收到邀请后，通过邮箱验证码激活和登录。系统不提供公开注册接口。公共完整简报及现有飞书群、PushPlus topic 推送继续保留。

未来产品化可以开放：用户输入自己的邮箱，系统向该邮箱发送验证码，验证成功后建立产品账号。继续采用无密码登录；后续可关联飞书等登录方式。

需要区分两个对象：

| 对象 | 代表什么 | 如何建立 |
|---|---|---|
| 产品账号 Account | 已完成邮箱验证的用户身份 | 开放注册或接受邀请后建立 |
| 团队成员 Membership | 某个团队中的成员资格、角色和内容权限 | 由该团队邀请，或由明确的加入申请流程批准 |

**自主注册只建立自己的产品账号。它不会自动加入现有课题组，也不会获得组内候选池、成员名单、个人简报或管理权限。** 同校邮箱、同邮箱后缀不能默认视作同一课题组成员。

## 2. 产品注册流程

1. 用户进入产品注册页，输入邮箱，确认适用的使用条款和隐私说明。
2. 服务端规范化并校验邮箱，实施发信频率与总预算限制。
3. 系统生成随机验证码，发送至该邮箱；前端只获得挑战 ID，不获得验证码。
4. 用户在发起请求的浏览器输入验证码。
5. 服务端核对用途、挑战、邮箱、浏览器、有效期、错误次数和单次使用状态。
6. 在同一个数据库事务内完成邮箱验证与账号创建，或者识别已有账号并转入登录。
7. 创建新会话，进入引导页，设置研究主题、关键词、内容类型和条数。
8. 根据当时产品策略，进入个人工作区、受限试用或等待名单。
9. 用户可主动接受团队邀请、申请加入团队；通过授权后才出现该团队内容。

邀请码和邮箱验证同时存在时，验证邮箱必须与邀请邮箱一致。已注册用户接受邀请，只新增团队成员关系，保留原有账号、个人空间和其他团队关系。

## 3. 首版产品开放方式

建议逐步开放，不直接把组内实例变成无门槛公共服务：

| 阶段 | 开放范围 | 出口条件 |
|---|---|---|
| A：组内稳定运行 | 仍为邀请制，约 5—20 人 | 登录、内容质量、备份恢复与成本有实际运行记录 |
| B：公开申请 | 用户验证邮箱并进入等待名单 | 能控制发信预算、名额与支持负担 |
| C：限额自助注册 | 用户可创建受限个人工作区 | 团队隔离、订阅限制、费用监控和故障关闭开关通过验收 |
| D：多团队产品 | 个人空间和邀请制团队并存 | 多租户权限、独立配额、迁移恢复、运维值守具备上线条件 |

早期产品账号默认进入个人工作区。邀请制课题组继续作为私有团队运行；公开注册开关与团队邀请开关相互独立。

## 4. 身份模型与迁移

当前 Phase 4 是单课题组服务：`users` 同时保存登录邮箱和组内角色。产品化之前需要拆分：

```text
Account
  accountId / status / createdAt
EmailIdentity
  accountId / normalizedEmail / verifiedAt / isPrimary
LoginIdentity
  accountId / provider / providerSubject / verifiedAt
Workspace
  workspaceId / type(personal|team) / status
Membership
  accountId / workspaceId / role / status / revision
Invitation
  workspaceId / email / role / tokenHash / expiry / acceptedBy
```

订阅、个人报告、反馈、渠道绑定、通知任务和审计事件都要包含明确的工作区归属。会话可以记录当前工作区，但每个请求仍需重新检查该工作区的成员关系，不能把浏览器提供的 `workspaceId` 当作授权凭据。

迁移步骤：

1. 备份并演练恢复现有单组数据。
2. 为现有课题组创建固定私有 Workspace。
3. 将现有成员映射为 Account 和 Membership，保留角色与停用状态。
4. 为历史订阅、版面、反馈补充工作区归属；保留原不可变版本内容和原始哈希，使用迁移映射表连接旧标识，不改写历史正文。
5. 迁移外部身份与绑定时，核对应用范围和用户控制权；未核对的绑定保持未启用。
6. 撤销旧会话，要求重新登录；个人外发队列保持暂停，核对迁移前后投递意图。
7. 验证新旧账号、团队和历史报告映射后再开放注册。

账号合并不能仅凭相同显示名称或第三方返回的未经验证邮箱。更换主邮箱需验证新邮箱，并通过当前身份的再次验证；应保留可追溯的变更记录。

## 5. 验证码与发信服务

### 当前可复用能力

Phase 4 已提供随机 8 位验证码、10 分钟过期、每挑战最多 5 次校验、浏览器绑定、单次使用、验证码 HMAC、数据库中的发信限流，以及生产 SMTP TLS 配置。服务端不向浏览器返回验证码，也不将验证码写入生产日志。

这些是组内默认值，产品化后需要根据真实误投率、重试率、邮件延迟和攻击流量调整，不能直接把单组配额作为公共服务容量。

### 产品阶段补充

- 为注册、登录、接受邀请和邮箱变更分别定义挑战用途，不能跨用途兑换。
- 使用可靠的事务邮件通道，明确发件身份、域名验证和退信处理。
- 增加待发送任务表，事务提交后由邮件任务进程发送；失败采用有上限的重试，任务幂等。
- 按邮箱、来源 IP、匿名设备和全站设置限额；同时设每日成本预算和管理员紧急关闭开关。
- 只有受控反向代理可以提供可信客户端地址，防止伪造 `X-Forwarded-For` 绕过限流。
- 普通请求响应避免泄露某邮箱是否已注册；邮件发送失败通过可追踪错误记录和客服流程排查。
- 根据异常请求风险逐步启用额外验证，不要求所有正常用户反复完成复杂挑战。
- 避免在邮件标题、链接和退信诊断里泄露研究订阅、个人简报或课题组私人信息。

本地开发邮箱只用于测试，不得作为产品邮件通道，也不得把它的目录放入静态站点。

## 6. 登录、接收渠道和账号关系

| 能力 | 产品含义 |
|---|---|
| 邮箱验证码登录 | 验证产品账号身份 |
| 飞书登录 | 将经过验证的飞书身份关联到账号，之后可用于登录 |
| 飞书接收绑定 | 明确个人简报发送给哪个已验证的飞书用户 |
| 微信接收绑定 | 明确个人简报发送给哪个已验证的好友/渠道目标 |

登录身份和通知绑定分别保存、分别撤销。用户取消飞书通知不等于删除账号；邮箱登录的用户可以只绑定微信。成员不手填任意 `open_id` 或 `chat_id`，也不提交自己的发送 Token。

产品化前重新核对飞书应用范围、跨组织使用方式和微信通道的实际能力及额度。现阶段没有把组内可用通道默认为所有外部用户均可用。

## 7. 内容、配额与成本

继续复用“统一抓取和审核、按用户确定性组装”架构。新增注册用户不会自动触发一套完整模型流水线。

产品阶段至少提供：

- 注册名额、每账号订阅数量、每日条数和外部发送频率上限。
- 个人空间与团队内容的阅读范围及来源授权边界。
- 共享加工预算和个人组装/存储/邮件预算分别统计。
- 对新主题或新来源的需求进入审核或预算流程，避免用户输入任意关键词就触发无限采集和模型调用。
- 模型故障、主题内容不足或预算耗尽时给出准确状态，不发送陈旧替代报告。

可付费产品的套餐、支付、退款和税务属于后续独立设计，本方案不直接接入支付或开通收费。

## 8. 数据、基础设施与运维

组内 Phase 4 使用单实例 Node 24 服务和 SQLite 持久数据库。公开注册和多实例之前迁移 PostgreSQL，并对邀请兑换、账号创建、请求幂等、成版和投递意图建立数据库唯一约束与事务测试。

同时完善：

- 正式域名、HTTPS、邮件服务、密钥管理和明确的服务负责人。
- 分离开发、测试、生产账号与凭证；测试永远使用合成内容和模拟邮件。
- 定期备份与恢复演练，记录可接受的数据恢复范围。
- 邮件、登录失败、权限拒绝、队列积压、模型预算和数据库容量监控。
- 账号停用、注销、个人数据导出与删除流程；共享候选、匿名统计和个人历史分别制定保留规则。
- 注册条款、隐私说明、邮件用途和通知退订在对应操作处明确告知；上线前按实际地区和产品形式核对适用要求。

私人订阅和个人报告继续只经认证 API 读取，不能使用公开 Pages 或不可猜测 URL 代替权限控制。

## 9. 组内功能如何保留

产品升级不得破坏现有组内使用：

1. 现有课题组保持私有，原角色和所有权保持。
2. 原公共完整简报与群体推送继续独立运行。
3. 原成员无需重新选择全部订阅；迁移后的主题版本变化应明确提示。
4. 管理员继续邀请和停用成员；公开用户不会自动出现在课题组成员列表中。
5. 个人通知异常时可单独关闭，不影响公共版生成与群推送。

## 10. 开放注册前验收清单

- 同邮箱并发注册只产生一个账号；验证码不能重放、跨浏览器或跨用途兑换。
- 未验证邮箱不能获得正式账号能力；邀请到期或撤销后不能激活团队资格。
- 自主注册用户不能访问已有团队；修改 URL、工作区 ID、成员 ID 或报告 ID 均不能越权。
- 已有账号接受团队邀请后正确新增成员关系，不复制账号或历史。
- 账号、团队成员停用和渠道解绑能即时阻止相应的访问和未发送任务。
- 5、20、100 个不同用户的组装测试不增加逐人完整模型流程；容量与预算满足选定的试用规模。
- 发信限额、失败重试、全站预算和紧急关闭开关经演练有效。
- 旧成员数据迁移和恢复经演练，无报告串属、权限扩大或重复通知。
- 支持负责人、发信账号、域名、预算及恢复操作有明确归属。

## 11. 实施顺序与保留接口

建议在 Phase 5 站内闭环、Phase 6 个人通知及 Phase 7 组内试用完成后，再启动产品化：

1. 完成组内稳定性观察与实际问题修复。
2. 将身份与团队成员关系拆分，完成 PostgreSQL 迁移演练。
3. 增加注册挑战用途、等待名单、邮件队列和全站限额。
4. 开放小批量邮箱自主注册，默认创建个人空间或进入等待名单。
5. 验证团队邀请、多空间切换及私人报告隔离。
6. 完成运行与支持准备后逐步扩大名额。

当前 `/api/member/auth/config` 固定返回 `registrationMode: "invite-only"`。未来可以扩展为 `invite-only`、`waitlist`、`open`，但必须先完成对应服务端权限和存储流程，不能只增加前端“注册”按钮或放宽邮箱白名单。
