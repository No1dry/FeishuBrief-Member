# Phase 4 技术决策记录

初始日期：2026-09-26。范围为单课题组邀请制试用；实现与本地验收不等于线上部署验收。本文保留 Phase 4 决策，末尾记录 2026-09-27 的 Phase 5 进展。

## 身份与权限

- 管理员邀请邮箱；用户以邮件中的 8 位验证码激活或登录。未邀请邮箱不会自动建立账号。
- 管理员通过本地 bootstrap 命令初始化，之后也必须通过邮箱验证登录。
- 首次邀请与后续登录使用同一个账号。邀请链接只携带片段令牌，前端读取后清除；验证码与发起登录的浏览器绑定。
- Cookie 会话为生产 Secure、HttpOnly、SameSite=Lax；会话及验证码均设置失效时间。修改角色、停用或退出撤销对应会话。
- Lab Owner 管理成员和全部主题；Topic Owner 仅维护授权主题；Member 管理本人订阅/反馈/报告；Viewer 只读。服务端每次请求检查会话、状态和权限。
- 所有读取和写入以当前会话身份为准。管理员不通过个人报告 API 读取他人的私人报告。
- 自主注册属于独立后续方案，当前接口固定 `registrationMode=invite-only`。

认证实现参考 [OWASP 身份验证](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)及[会话管理建议](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)；本次验收侧重可执行的身份、限流、撤销和越权测试。

## 独立服务与数据库

新建 `FeishuBrief-Member`，与内容引擎、Console 前端分开。使用 Node 24.21、原生 HTTP、TypeScript、Zod 和 SQLite，数据库迁移文件随独立工程管理。

组内约 5—20 人采用单进程/单服务器和本地持久磁盘。SQLite 开启外键、WAL、写入超时；关键变更在同步事务内执行。事务不得跨越 SMTP 等异步操作。使用数据库在线备份接口，而不是只复制可能仍依赖 WAL 的主文件。

选择 SQLite 是本阶段部署规模的明确取舍，调整了原方案中“建议优先验证 PostgreSQL”的选型。Node 24 文档将 `node:sqlite` 标为 Release Candidate，因此锁定已测试的 Node 版本；每次运行时升级均需回归。多实例、公开注册或多租户之前迁移 PostgreSQL，不将当前同步数据库访问方式直接扩大使用。[Node SQLite 文档](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html)

## 前后端部署

成员界面固定使用同源 `/api/member/`。生产部署将构建好的 Console 与 API 放在同一个 HTTPS 来源，可以由 Member Service 提供静态文件，也可以由反向代理分流。

Phase 4 的 `/app` 提供成员登录、雷达和组内管理员的成员管理入口；原 `/admin` 保留旧内容引擎 GitHub 工作台。前端路由、GitHub 凭证与成员会话保持隔离。当时将完整成员简报、订阅、历史和主题负责人页面列入 Phase 5；这些界面现已完成，见下文补记。

GitHub Pages 不能单独承载这一 Cookie 会话服务。部署配置必须明确域名、证书、数据库磁盘、发信账号和备份责任人；当前尚未获得这些生产配置。

## 邮件

使用 SMTP 适配器，可注入模拟邮箱进行测试。生产连接要求 TLS 和证书验证，发件身份、SMTP 地址、账号、密码从环境变量读取。SMTP 配置遵循 [Nodemailer 官方文档](https://nodemailer.com/smtp)。

邀请和验证码在组内阶段由请求发送，具有连接超时和发信限额；发送失败会撤销对应未完成挑战或邀请，并记录不包含验证码的审计信息。没有把 SMTP 受理表述为用户已收到。产品阶段增加可靠邮件队列、退信处理和全站成本控制。

本地 `local` 邮箱模式只在明确开启的 loopback 开发配置下可用，邮件写入私有目录。不会在 HTTP 响应或日志中提供调试验证码接口。验收没有发送真实邮件。

## 内容导入和主题权威来源

机器接口与浏览器会话分开认证。导入包包含原始候选、共享审核批次、冻结主题配置、候选快照与撤销列表。服务端验证哈希、字段、可见性、证据和引用关系，重建快照一致后在一个事务内写入 ready 状态。

首次导入初始化服务端目录。此后 Topic Owner 或管理员修改主题后，旧主题评估不能继续成为新雷达/个人组装的输入。内容引擎必须拉取当前服务主题再重新审核，服务端才能接受匹配的新批次。

启用服务目录为生产权威源时，需先关闭旧 Console 对 `researchTopics` 的写入（从引擎的 `supportedConfigPaths` 删除该项并发布），再启用引擎的服务主题配置路径；不能让两个入口继续编辑同一套生效主题。当前未进行该生产切换，公共版保持原流程。

撤销可以独立于新内容 ready 导入：即使目录已修改、内容还在重新处理，也先阻止已撤销内容展示。引擎上传命令按“撤销 → 内容导入”顺序执行，失败不会放宽已完成的撤销。

## 个人版与当前边界

个人预览复用 Phase 3 的纯函数，不调用模型或产生收录历史。正式站内成版在数据库事务中读取当前订阅、反馈、历史和内容，记录不可变版本与请求幂等键。空结果不进入正式收录历史。

服务端保存完整可重放协议；对成员返回省略内部诊断的展示投影。该投影不是可回放的完整 PersonalEdition。历史版本在展示前仍检查当前权限和撤销状态。

Phase 6 已增加独立个人飞书/微信绑定、持久投递和个人调度；默认不运行消费者和计划，真实平台验收待配置。已有群体完整简报、飞书群和 PushPlus topic 发送器保持原状。详见 [Phase 6 实现](phase6-implementation.md)。

## Phase 5 补记（2026-09-27）

完整成员及管理 Console 已实现，包含个人订阅和草稿预览、站内简报与历史深链接、内容库、收藏/反馈、成员管理、主题管理及运营审计。具体入口、交互和本机复现步骤见 [Phase 5 实现说明](https://github.com/No1dry/FeishuBrief-Console/blob/main/docs/phase5-implementation.md)。

成员服务新增能力、内容库、本人活跃反馈和管理员运行汇总接口。草稿预览不保存订阅或推进历史；历史收藏逐条检查当前权限和撤回状态；运行汇总仅返回实际批次元数据和组装计数，不暴露他人的订阅或正文。Member 类型检查及 29 项测试通过，覆盖服务逻辑和真实本机 HTTP 接口。

生产服务按入口设置完整 CSP：成员页面仅连接同源 API，原管理员工作台另允许 GitHub API。跨入口整页加载；会话退出、隐藏标签及跨标签变化清空旧内容并重新验证。部署配置继续使用同源 HTTPS 和单实例 SQLite。

当前仍为本地实现和验证，生产域名、线上服务器及真实 SMTP 尚未部署或验收。Phase 6 能力接口按配置显示个人渠道和调度状态，默认关闭，真实收件验收另行完成；现有群体完整简报继续保留。邮箱自主注册仍是保留的后续产品化方案。
