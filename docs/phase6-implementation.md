# Phase 6：个人通知、绑定与投递队列

## 边界与启用方式

个人通知由独立 Member Service 保存和投递。内容继续复用经过证据验证的共享候选，个人组装不调用模型。现有引擎的飞书群消息、PushPlus topic 和公开完整简报继续使用原流程。

部署默认关闭后台投递和定时组装。配置平台凭据、完成成员绑定后，运维显式设置 `MEMBER_NOTIFICATION_WORKER_ENABLED=true`；需要每日自动组装时再设置 `MEMBER_SCHEDULER_ENABLED=true`。后者要求前者开启。成员还必须在 Console 打开自己的计划。保存订阅、预览、生成站内版本均不会直接发送消息。

| 服务端配置 | 用途 |
| --- | --- |
| `MEMBER_FEISHU_APP_ID` / `MEMBER_FEISHU_APP_SECRET` | 自建应用机器人身份 |
| `MEMBER_FEISHU_ENCRYPT_KEY` / `MEMBER_FEISHU_VERIFICATION_TOKEN` | 验证并解密飞书回调；四项一起配置 |
| `MEMBER_PUSHPLUS_TOKEN` / `MEMBER_PUSHPLUS_SECRET_KEY` | 私人发送账号和开放接口长期密钥；短期 accessKey 自动获取、缓存、刷新 |
| `MEMBER_NOTIFICATION_WORKER_ENABLED` | 默认 `false`，启用持久队列消费者 |
| `MEMBER_SCHEDULER_ENABLED` | 默认 `false`，启用成员每日计划 |
| `MEMBER_NOTIFICATION_POLL_MS` | 默认 15000，允许 1000–60000 毫秒；同一进程不重叠运行 |

配置不读取旧的 `FEISHU_CHAT_ID`、`FEISHU_APP_SECRET`、`PUSHPLUS_TOPIC` 或 `PUSHPLUS_TOKEN`。所有凭据只留在服务端，成员页面不接收发送 Token、好友 Token 或飞书 open_id。

## 飞书绑定

1. 在飞书开放平台启用应用机器人，配置应用可用范围、私聊消息接收及发送所需权限，并发布供组内使用。
2. 事件订阅选择 `im.message.receive_v1`，回调为 `https://<成员服务域名>/api/member/webhooks/feishu`，配置 Encrypt Key 与 Verification Token。代理应保留原始请求体和 `X-Lark-*` 请求头。
3. 登录 Console → 个人通知 → 开始飞书绑定，获得限时一次性绑定码。
4. 成员在飞书中找到该应用机器人，**私聊**发送页面显示的绑定指令。群消息不能绑定。
5. 服务端验证签名、时间窗口、解密内容、应用和事件身份，登记真实消息发送者；成员回到原登录会话确认后绑定生效。

成员无需填写会话 ID。机器人必须对该成员可用；平台管理后台授权及应用发布仍需运维完成。

## 微信 / PushPlus 好友绑定

1. 使用具备好友功能及开放接口权限的 PushPlus 发送账号，设置 Token 和 secretKey。实际额度以账号当前配置为准，不在代码中假定固定每日额度。
2. 在 PushPlus 个人中心设置回调 `https://<成员服务域名>/api/member/webhooks/pushplus`。该接口只处理绑定线索；消息结果不凭匿名回调直接置为成功。
3. 成员在 Console 开始微信绑定，扫描本次挑战生成的限时好友二维码。图片由同源受认证接口读取，不放宽 Console 的外部连接策略。
4. 回调中的好友身份需经服务端开放接口核实。随后向该单个好友发送一次性绑定验证码，成员在原 Console 会话输入正确验证码后才启用绑定。
5. 若未收到好友回调、已存在好友导致平台没有产生新的事件，或账号没有对应权限，页面不会自动判定成功。已存在好友的重复扫码行为需在实际账号验收；若平台不产生 `add_friend` 事件，需要成员和管理员在 PushPlus 确认解除旧好友关系后重新扫码。本服务不会自动删除平台好友，也不能手工写入好友 Token 跳过验证。

启动微信绑定会在扫码并核实好友后发送验证消息，这是成员的显式绑定操作。自动化验证全部使用注入的模拟平台，不发送真实验证码。

## 固定版本、状态与重复控制

每个投递任务固定引用成员、个人简报版本、渠道、绑定版本、目标及消息内容哈希。自动任务按“成员＋报告日期＋daily”去重；显式投递与补发使用稳定 `requestId`。管理员补发必须填写原因并确认重复风险，操作留审计。

| 状态 | 含义与处理 |
| --- | --- |
| `queued` | 已入队，尚未发送 |
| `sending` | 已取得发送资格，正在请求平台 |
| `accepted` | 平台接受请求；不能解释为成员已读 |
| `provider_confirmed` | 经平台查询确认发送成功；仍不表示成员已读 |
| `retryable_failed` | 已明确未受理的临时失败，按退避与限频再试 |
| `permanent_failed` | 明确不可自动恢复或已用完重试次数 |
| `unknown` | 超时、中断等无法断定是否受理；不自动重发 |
| `cancelled` | 暂停、解绑、账号/权限变化等取消尚未发送的任务 |

结果未知时，管理员先核对平台结果。当前适配器支持 PushPlus 消息 ID 查询；飞书和没有消息 ID 的超时采用人工核对，仍保留 `unknown`。如经外部核对仍决定补发，需先记录核对说明，再明确确认重复风险，产生独立补发记录。同一版本仍存在未决投递时不能通过选择旧的成功记录绕过核对。

订阅暂停、渠道解绑、停用账号和修改授权会在数据库事务中取消未发送任务。发送前再次验证账号、订阅、绑定、内容权限及撤回状态，包括异步获取平台令牌之后、真正发请求之前。已经交给平台的网络请求无法撤回；它的实际返回仍保留在审计和投递状态中。

## 定时与日常操作

首版组内计划使用 `Asia/Shanghai` 时区和 `HH:mm` 本地时间。每名成员独立开关；工作日计划遵循该时区。没有当天可用内容时不把昨天的简报当成今日版发送；没有合格新条目时不发送空通知。

后台运行在唯一 Member Service 进程中，不另启并发 cron 或第二个实例。队列、尝试记录、限流、计划和幂等键持久化在 SQLite。停机先停止接收新请求并等待进行中的工作结束，再关闭数据库；崩溃留下的发送任务按未知结果处理。

默认每个渠道至少间隔 10 秒；明确的临时拒绝从 30 秒开始指数退避，同时遵守平台返回的更长等待时间，最多尝试 3 次。永久拒绝或不确定结果不进入自动重试。好友查询最多扫描 20 页、每页 50 人，超出范围关闭该次绑定并由运维检查账号，不自动扩大接口调用量。

个人消息提供站内私有版本入口。链接仍要求邮箱登录和本人权限，不含免登录凭据，也不把私人内容发布到 Pages。主题读取权撤销、内容撤回后，站内入口仍会拒绝访问。

## 验证与上线验收

本地验证使用合成成员、临时 SQLite、注入邮件/平台和本地 HTTP。覆盖身份归属、签名与重放、一次性验证码、跨成员隔离、稳定版本、幂等、重试、未知结果、暂停解绑、账号停用、定时计划及 Console 操作。不使用真实飞书、微信、SMTP 或 LLM。

2026-09-27 验证记录：

- Member `npm test`：最终 **64/64** 通过；TypeScript 检查通过，引擎副本 **4 文件**一致性通过。
- Console：全套 **69 项**通过；之后两项边界修复/新增用例由最终 **11 项通知专项**全部通过覆盖，当前共 71 项用例；最终构建通过。
- 真实本机 HTTP＋生产构建＋Chrome：邮箱登录、站内成版、签名加密飞书回调、页面确认绑定、明确发送、重复 worker 不重发、保存定时、管理员补发与解绑取消全部通过。实际使用 3 封内存邮件、1 次模拟投递、0 次外网/模型请求。
- 已目检通知桌面和手机截图；账号切换、越权版本、登出及成员/管理员 CSP 边界继续通过。
- 交叉审查额外修复：手动与定时交错重复发送、选择旧记录绕过未知补发、解绑闲置渠道误取消另一渠道计划，以及目录变化后的固定版本崩溃恢复。

联调脚本为 `FeishuBrief-Console/scripts/check-member-live.ts`，从 Member 目录执行 `node --import tsx ../FeishuBrief-Console/scripts/check-member-live.ts`，需先构建 Console，并安装本机 Chrome。脚本只创建临时合成数据，不读取业务凭据或启动后台调度。

生产验收需要实际 HTTPS、SMTP、自建飞书应用、PushPlus 账号及两位组内测试成员。应先在关闭定时任务的情况下，各自绑定并手动投递一个小样本，核对收件人和不同订阅的内容，再开启小范围计划。当前本地实现和模拟验证不能替代平台账号权限、额度、回调公网可达性和真实收件验证。
